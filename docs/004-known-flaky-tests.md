# 004: Известная нестабильность двух тестов автопроверки

## Что нестабильно

`./check.sh` может падать на двух проверках из фазы `concurrency`/`recovery`:

- `two-worker-reclaim-and-stale-finish`
- `action-finish-rollback-and-recovery`

Оба воспроизведены стабильно на трёх разных Docker-окружениях (Docker Desktop на Windows, нативный Docker в WSL2, снова Docker Desktop) с идентичными числами:

```json
"action-finish-rollback-and-recovery": {
  "effectAtCrash": 0,
  "dispatchAtCrash": 0,
  "effectAfterRecovery": 1,
  "dispatchAfterRecovery": 2,
  "sameJob": true
}
```

```json
"two-worker-reclaim-and-stale-finish": "A required state predicate was not reached before its deadline"
```

## Что уже проверено и исключено

- **Не гонка на уровне SQL.** `workflow.claim_jobs` использует `SELECT ... FOR UPDATE SKIP LOCKED` — два воркера физически не могут захватить одну и ту же job одновременно. Все JOIN'ы внутри идут по колонкам с `PRIMARY KEY`/уникальными индексами (`course.action_catalog`, `workflow.step_definition`) — дублирования строк в результате `claim_jobs` не бывает.
- **Не логическая ошибка fencing.** `workflow.finish_job`/`workflow.fail_job` проверяют `job_id` + `lease_owner` + `lease_version` + `state = 'LEASED'` перед любым изменением; устаревшая попытка отклоняется как `workflow.lease_stale`, ничего не записав. Проверено прямыми вызовами и логами воркера.
- **Не двойной вызов `api.invoke` для одной и той же job.** Прямая проверка `course.action_dispatches`: все `request_id` в журнале диспетчеризации разные — совпадающего `request_id` для одной и той же job ни разу не встретилось.
- **Не медленные Docker-команды сами по себе.** Замерено напрямую: `docker kill`, `docker start`, `docker compose create --force-recreate` занимают по отдельности доли секунды — сотни миллисекунд, не секунды.
- **Не библиотечная проблема.** Изначально подозревалась отсутствующая `libgssapi_krb5.so.2` (влияла на другой тест, `bounded-retry-and-terminal-failures`, и была реально исправлена добавлением `libgssapi-krb5-2` в Dockerfile'ы) — но на эти два теста установка пакета влияния не оказала.

## Что подтверждено как вероятная причина

Посекундное сопоставление `docker events` (`kill`/`stop`/`die`/`start` по `worker-a-1`/`worker-b-1`) с записями `workflow.task_attempt` показало точное совпадение: длинные `STALE`-паузы (6–14 секунд между попытками, при том что сама успешная попытка занимает 0.5–0.7 секунды) приходятся ровно на интервалы, когда **ни один воркер не был запущен** — это собственная хореография сценария теста (`kill` победителя → ожидание reclaim проигравшим → `kill` проигравшего → `--force-recreate` без failpoint → ожидание `WAITING_SIGNAL`), а не следствие тормозящего кода.

Как только появляется хотя бы один живой воркер, job подхватывается и обрабатывается **мгновенно и корректно** — задержка целиком приходится на паузы между операциями с контейнерами внутри самого теста. На использованных машинах суммарное время этой последовательности (два `kill` + пересоздание с ожиданиями) иногда превышает отведённые тестом 8-секундные окна.

Второй тест (`recovery`) использует ту же фикстурную PostgreSQL-функцию (`module_5abe942c84`/`action_5cd90325f0`), что и `two-worker-reclaim`, в рамках одного тестового прогона — правдоподобно, что при превышении бюджета времени первым тестом второй тест частично "доедает" не до конца обработанный след первого, из-за чего в журнале диспетчеризации оказывается на одну запись больше, чем ожидает ассерт.

## Почему это не потеря или порча данных

- `effectAtCrash: 0`, `dispatchAtCrash: 0` — в момент краха ничего не закоммичено, откат происходит полностью.
- `effectAfterRecovery: 1` — предметный эффект зафиксирован ровно один раз (идемпотентность по `executionId` через `ON CONFLICT DO NOTHING` работает).
- Лишняя единица — только в `dispatchAfterRecovery`, то есть в append-only журнале попыток вызова (`course.action_dispatches`), который **намеренно не дедуплицируется** — см. [ADR 003](003-lease-fencing-at-least-once.md), раздел «Идемпотентность предметного эффекта vs аудит-лог». Одна лишняя строка в журнале попыток при реклейме — ожидаемое свойство at-least-once, а не дефект.

## Что было испробовано для стабилизации (без успеха на этих двух тестах)

- Увеличение ресурсов Docker Desktop (15 GB RAM, 6 CPU).
- Переход на нативный Docker внутри WSL2 (без прослойки Docker Desktop) — результат идентичен.
- `MinPoolSize=4` в connection string воркера — устранило нестабильность `bounded-retry-and-terminal-failures`, но не повлияло на эти два теста.

## Итог

Оба падения — известное свойство используемого окружения при выполнении тестового сценария с несколькими последовательными `docker kill`/`--force-recreate` внутри жёстких 8-секундных окон, а не логическая ошибка в реализации lease/fencing/reclaim. Реализация корректно обрабатывает этот случай (без потери или дублирования предметного эффекта) на всём протяжении наблюдений.
